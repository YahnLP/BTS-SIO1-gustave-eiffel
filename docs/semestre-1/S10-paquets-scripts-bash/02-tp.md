## Partie A – Gérer des paquets avec `apt` (≈ 50 min)

**But :** installer, examiner et supprimer un logiciel proprement. On utilise `tree`, qui affiche une arborescence : il te servira à vérifier ton script de la partie D.

| Étape | Je fais | J'anticipe | Je constate |
|---|---|---|---|
| 1 | Taper `tree`, puis `which tree` | | |
| 2 | `apt show tree` : lire la description, la version et les dépendances | | |
| 3 | `sudo apt update`. Lire les lignes affichées | | |
| 4 | `sudo apt install tree`. Lire **tout** ce qu'`apt` annonce **avant** d'installer | | |
| 5 | `tree ~` (ou le dossier `CommandesLinux` de S09) | | |
| 6 | `dpkg -L tree` | | |
| 7 | `apt list --upgradable`, puis `apt -s upgrade` (`-s` : **simulation**, rien n'est installé) | | |
| 8 | `sudo apt remove tree`, puis `which tree` | | |

**Je comprends.**

1. À l'étape 3, `apt update` a-t-il **installé** quelque chose sur ta machine ? Qu'a-t-il fait ? ______________________
2. À l'étape 4, `apt` a-t-il annoncé l'installation d'autres paquets en plus de `tree` ? Comment s'appellent-ils, et pourquoi ? ______________________
3. Que montre `dpkg -L tree` (étape 6) ? Où sont rangés les fichiers du programme ? ______________________
4. Quelle différence y a-t-il entre `remove` et `purge` ? Pourquoi `apt -s upgrade` est-il utile avant une vraie mise à jour sur un serveur ? ______________________
5. Pourquoi `apt` installe-t-il des paquets **signés** depuis des dépôts, plutôt que de laisser chacun télécharger un programme sur Internet ? ______________________

<details markdown="1">
<summary>Éléments de réponse</summary>

1. Non : `apt update` ne fait que **rafraîchir la liste** des paquets proposés par les dépôts.
2. Selon l'image de la VM, `tree` peut n'avoir **aucune** dépendance à ajouter ; si `apt` annonce d'autres paquets, ce sont des **dépendances** dont `tree` a besoin pour fonctionner.
3. La liste de tous les fichiers installés par le paquet (programme dans `/usr/bin`, page de manuel, documentation…).
4. `remove` supprime le programme et garde la configuration ; `purge` supprime aussi la configuration. La simulation montre ce qui **serait** modifié, ce qui permet de contrôler avant d'agir sur un serveur en production.
5. Un dépôt officiel garantit l'origine et l'intégrité des paquets (signature vérifiée) et permet de les **mettre à jour** de façon centralisée.

</details>

**Réinstalle `tree`** (`sudo apt install tree`) pour la suite.

## Partie B – Mon premier script (≈ 45 min)

**But :** écrire, rendre exécutable et lancer un script simple.

1. Crée un dossier `scripts` et va dedans.
2. Crée un fichier `bonjour.sh` contenant : le shebang, un commentaire, puis des commandes qui affichent **ton prénom**, le **nom de la machine** (`hostname`) et la **date** (`date`).
3. Lance-le avec `bash bonjour.sh`, puis avec `./bonjour.sh`. Que constates-tu ?
4. Rends-le exécutable (`chmod +x bonjour.sh`) et relance `./bonjour.sh`.
5. Modifie le script pour qu'il affiche un message **personnalisé avec le premier argument** : `./bonjour.sh Alice` doit afficher « Bonjour Alice ».
6. Que se passe-t-il si tu le lances **sans** argument ? Améliore-le pour qu'il utilise une valeur par défaut dans ce cas (relis la syntaxe `${1:-…}`).

**J'anticipe.** Avant l'étape 3, que va donner `./bonjour.sh` si le fichier n'a pas le droit d'exécution ? ______________________

**Je comprends.**

1. Pourquoi faut-il écrire `./` devant le nom du script ? ______________________
2. À quoi sert la première ligne `#!/bin/bash` ? Que se passe-t-il si on l'oublie ? ______________________
3. Quelle commande vérifie la syntaxe d'un script **sans** l'exécuter ? ______________________

<details markdown="1">
<summary>Éléments de réponse</summary>

Avant l'étape 4, `./bonjour.sh` échoue (« Permission denied »), alors que `bash bonjour.sh` fonctionne.

1. Le dossier courant n'est pas dans les dossiers où le shell cherche les programmes ; `./` désigne explicitement le dossier courant.
2. Le shebang indique **quel interpréteur** doit exécuter le fichier. Sans lui, le script peut être interprété par un autre interpréteur que Bash, avec des comportements différents.
3. `bash -n bonjour.sh`.

</details>

## Partie C – Tester et répéter (≈ 50 min)

**But :** découvrir les conditions, les boucles et la notion de script relançable, **sur un exemple sans rapport avec JackCelair**.

### C1. Une condition

Écris `existe.sh` qui reçoit un nom en argument et affiche :

- « C'est un dossier » si c'est un dossier existant ;
- « C'est un fichier » si c'est un fichier ordinaire existant ;
- « N'existe pas » sinon.

Teste avec : `/etc`, `/etc/hostname`, `/nimportequoi`, et un nom **avec un espace** : `./existe.sh "mon dossier"`.

**J'anticipe.** Si tu oublies les guillemets autour de `$1` dans le test, que va-t-il se passer pour `"mon dossier"` ? ______________________

### C2. Une boucle et un script relançable

Dans `/tmp`, on veut créer trois dossiers : `rapport`, `mon dossier` et `autre dossier`.

1. Écris `dossiers1.sh` qui les crée avec une **boucle** `for` et la commande `mkdir "$d"`, dans `/tmp/essai`. Lance-le **deux fois** de suite.
2. Écris `dossiers2.sh` identique, mais avec `mkdir -p`. Lance-le deux fois.
3. Écris `dossiers3.sh` qui **teste** d'abord avec `if [ -d … ]` et affiche « créé » ou « déjà présent ». Lance-le deux fois.

| Script | 1re exécution | 2e exécution |
|---|---|---|
| `dossiers1.sh` (`mkdir`) | | |
| `dossiers2.sh` (`mkdir -p`) | | |
| `dossiers3.sh` (test `if`) | | |

**J'anticipe.** À la **deuxième** exécution de `dossiers1.sh`, que va afficher `mkdir` ? Est-ce un problème pour un script d'administration ? ______________________

**Je comprends.**

1. Pourquoi le script 1 n'est-il pas « relançable » proprement ? ______________________
2. Que fait `mkdir -p` de plus ? Quel est l'**avantage** du script 3 sur le script 2 pour l'administrateur qui le lit dans les messages ? ______________________
3. Que se passerait-il avec `for d in rapport mon dossier autre dossier` (sans guillemets autour des noms) ? ______________________

<details markdown="1">
<summary>Éléments de réponse</summary>

1. À la seconde exécution, `mkdir` signale « File exists » pour chaque dossier : le script affiche des erreurs même si le résultat voulu est atteint.
2. `mkdir -p` ne signale pas d'erreur si le dossier existe, et crée les parents manquants. Le script 3 **dit ce qu'il a fait** (créé ou déjà présent), ce qui permet de contrôler l'état.
3. Le shell découperait la liste en cinq mots : `rapport`, `mon`, `dossier`, `autre`, `dossier` ; les noms avec espace ne seraient pas créés correctement.

</details>

## Partie D – Le script de création de l'arborescence (≈ 60 min, individuel)

**But :** écrire **toi-même** un script qui crée l'arborescence de JackCelair.

### D1. Le sujet

L'arborescence à créer est celle de [S08](../S08-terminal-commandes-de-base/02-tp.md) ([modèle](../S08-terminal-commandes-de-base/tp/arborescence-attendue.txt)) : 12 dossiers, noms avec espaces et accents.

**Contraintes (obligatoires) :**

- le script s'appelle `nom_prenom_create_tp.sh` et commence par un **shebang** ;
- il crée l'arborescence **en une exécution**, sous le dossier `$HOME/partage-test` (pas dans `/var/partage` : pas besoin de `sudo`) ;
- il **affiche** au moins un message clair sur ce qu'il fait ;
- il peut être **relancé sans erreur** et sans rien casser ;
- il **gère un dossier déjà présent** (il le signale, il ne plante pas) ;
- il **gère une erreur de création** : message clair, arrêt propre avec un code de retour non nul.

**J'anticipe (avant d'écrire).** Écris sur papier le **plan** de ton script en français : variables, liste, boucle, tests. Quels sont **les trois pièges** de cette arborescence ? ______________________

### D2. Les règles sur l'IA

> [!WARNING]
> **Il est interdit** de demander à une IA le script complet. Le copier-coller d'un script « tout fait » n'a aucun intérêt pédagogique. Tu peux utiliser une IA **pour comprendre** : une commande, un message d'erreur, comment rendre un script exécutable, comment tester l'existence d'un dossier.
>
> **Obligation :** tenir le **journal des prompts** de la [grille d'auto-évaluation](tp/grille-evaluation-script.txt) : chaque prompt saisi, **ce que tu en as retenu**, et **ce que tu as vérifié ou modifié toi-même**. L'objectif est de montrer que **tu as appris**, pas que tu as récupéré une solution.

### D3. Aides graduées (n'ouvre la suivante qu'après avoir cherché)

<details markdown="1">
<summary>Aide 1 : comment organiser le script</summary>

Mets **tout ce qui peut changer** (le dossier de base, la liste des dossiers) **en haut** du script, dans des variables. Le reste du script ne contient que de la logique : une boucle sur la liste, un test, un `mkdir`, un message.

</details>

<details markdown="1">
<summary>Aide 2 : les chemins à plusieurs niveaux</summary>

`mkdir -p` crée **les dossiers intermédiaires**. Tu n'as donc pas besoin de créer `commerce` avant `commerce/vente` : il suffit que ta liste contienne les chemins **des dossiers du bas** de l'arborescence.

</details>

<details markdown="1">
<summary>Aide 3 : stocker plusieurs noms, dont certains contiennent des espaces</summary>

Tu peux écrire une liste Bash entre parenthèses, chaque élément entre guillemets, et la parcourir :

```bash
LISTE=("un élément" "autre élément" "troisième")
for e in "${LISTE[@]}"; do
    echo "$e"
done
```

La notation `"${LISTE[@]}"` conserve les éléments **entiers** (espaces compris).

</details>

### D4. Je vérifie

1. `bash -n nom_prenom_create_tp.sh` : pas d'erreur de syntaxe.
2. Lance le script **une première fois** : l'arborescence est créée. Vérifie avec `tree "$HOME/partage-test"` et compare avec le [modèle](../S08-terminal-commandes-de-base/tp/arborescence-attendue.txt). **Capture d'écran.**
3. Lance-le **une seconde fois** : aucune erreur, les dossiers sont signalés comme déjà présents. **Capture d'écran.**
4. **Teste l'erreur** : change temporairement le dossier de base en `/root/essai` (interdit pour toi). Le script doit afficher un message clair et s'arrêter. Vérifie le code de retour avec `echo $?`. **Capture d'écran.** Remets ensuite le bon dossier de base.
5. Remplis la **grille d'auto-évaluation**.

**Je comprends.**

1. Pourquoi est-il important que ce script soit **relançable** (idempotent) dans une entreprise qui a plusieurs agences ou qui reconstruit des serveurs ? ______________________
2. Quels sont les **trois pièges** que tu as rencontrés (ou évités) ? ______________________
3. Quand tu écris en dur dans le script `/var/partage/JackCelair`, que se passe-t-il pour un utilisateur sans `sudo` ? Comment l'éviter ? ______________________

<details markdown="1">
<summary>Éléments de réponse</summary>

1. Un script d'administration est relancé : après une panne, sur une nouvelle machine, par un collègue. S'il échoue ou détruit quelque chose au deuxième passage, il est dangereux ; relançable, il converge vers le même état.
2. Les noms avec **espaces** (guillemets), les noms avec **accents**, l'**existence préalable** des dossiers (messages d'erreur à la relance). Selon la solution : l'oubli des guillemets autour de la variable dans la boucle.
3. Il obtient « Permission denied » sur `/var`. On évite en rendant la base **configurable** (variable ou argument), avec un dossier par défaut dans le dossier personnel, et en n'utilisant `sudo` que pour l'installation finale.

</details>

## Partie E – Pour aller plus loin (facultatif)

Ajoute à ton script **au moins deux** améliorations :

1. **Paramétrage :** le dossier racine peut être donné en argument (`./script.sh /chemin/vers/dossier`), avec le dossier par défaut sinon.
2. **Simulation :** une option (par exemple `-n`) affiche ce qui **serait** créé sans rien créer.
3. **Récapitulatif :** à la fin, le script affiche proprement l'arborescence créée (le nombre de dossiers créés et déjà présents).
4. **Gestion des erreurs avancée :** si un chemin est invalide ou non accessible, message clair et arrêt propre.

Teste ensuite ton script en l'exécutant avec `sudo` sur `/var/partage` (après avoir sauvegardé ou supprimé l'arborescence de S08). Que se passe-t-il pour **le propriétaire** des dossiers créés ? ______________________
