## Partie B – Sauvegarder des fichiers et prouver la restauration (≈ 50 min)

**Contexte.** Sur ta VM Debian, un dossier `~/donnees-jackcelair` contient les fichiers à protéger. Crée-le avec quelques sous-dossiers et une quinzaine de fichiers de test.

**J'anticipe.**

1. Quelle différence entre copier un dossier avec `cp -r` et le synchroniser avec `rsync` ? ______________________
2. Comment prouveras-tu que la restauration est **fidèle** ? ______________________

### B1. Un support distinct

Ajoute un **second disque virtuel** à la VM (VirtualBox, VM éteinte), redémarre, puis :

```bash
lsblk
```

Repère le **nouveau disque** (vide, sans partition). **Vérifie** son nom, puis crée un système de fichiers et monte-le dans `/mnt/sauvegarde` (`mkfs.ext4`, `mkdir`, `mount` : cherche la syntaxe avec `man`). Note les commandes dans le journal.

**Je comprends.** Pourquoi un second **disque** est-il préférable à un second **dossier** sur le même disque ? Que ne protège-t-il toujours pas ? ______________________

### B2. Archive et synchronisation

```bash
tar -czf /mnt/sauvegarde/donnees-$(date +%F).tar.gz -C ~ donnees-jackcelair
tar -tzf /mnt/sauvegarde/donnees-$(date +%F).tar.gz | head
rsync -a --dry-run -v ~/donnees-jackcelair/ /mnt/sauvegarde/miroir/
rsync -a ~/donnees-jackcelair/ /mnt/sauvegarde/miroir/
```

**Je comprends.**

1. Que fait chaque option de `tar -czf` ? Et `-C` ? ______________________
2. À quoi sert `--dry-run` ? Pourquoi le lancer avant ? ______________________
3. Modifie un fichier, ajoute-en un, supprime-en un, puis relance `rsync -a` **sans** `--delete`, puis **avec**. Que constates-tu ? Quel est le **danger** de `--delete` ? ______________________

### B3. Restaurer et prouver

1. **Simule un sinistre** : supprime le dossier `~/donnees-jackcelair`.
2. **Restaure** depuis l'archive dans un dossier de test (`/tmp/restauration`), pas par-dessus l'original.
3. **Prouve** que c'est fidèle : calcule des empreintes avant (stockées dans un fichier) et après, ou compare les dossiers avec `diff -r`.
4. **Mesure** la durée de la restauration (= RTO mesuré) et ce que tu as perdu entre la dernière sauvegarde et le sinistre (= RPO mesuré). Remplis le journal.

**Je comprends.** Que prouve une comparaison par **empreinte** que ne prouve pas « j'ai ouvert un fichier et il avait l'air bon » ? ______________________

<details markdown="1">
<summary>Éléments de réponse</summary>

1. `rsync` ne copie que ce qui a changé et peut refléter les suppressions ; `cp -r` recopie tout à chaque fois.
2. En comparant les contenus de l'original (ou ses empreintes calculées avant) et de la restauration.
- B1 : un disque distinct protège d'une panne du **premier** disque. Il ne protège pas d'un sinistre du local, d'une suppression par erreur **répliquée**, ni d'un logiciel de rançon si le disque reste monté.
- `tar -czf` : **c**réer une archive, compresser avec **z** (gzip), nommer le fichier (**f**) ; `-C` : se placer dans un dossier avant d'archiver (évite d'embarquer le chemin complet).
- `--dry-run` : montre ce qui serait fait sans le faire : on évite un effet de bord.
- Sans `--delete`, la copie garde le fichier supprimé ; avec, elle le supprime aussi : **utile** pour un miroir fidèle, **dangereux** si l'original est supprimé par erreur (la suppression se propage et la copie disparaît aussi).
- Empreinte : elle détecte une **différence d'un seul octet**, ce qu'un coup d'œil ne voit pas.

</details>

## Partie C – Sauvegarder et restaurer la base de GLPI (≈ 40 min)

Sur la **VM GLPI** (S13 et S14). **Snapshot** d'abord.

**J'anticipe.** Pour pouvoir remettre GLPI en service après la perte du serveur, que faut-il sauvegarder en plus de la **base de données** ? ______________________

**À faire.**

1. **Exporte** la base : 

```bash
sudo mysqldump --single-transaction glpi > ~/glpi-$(date +%F).sql
ls -l ~/glpi-*.sql
```

2. **Retrouve** dans la documentation de ta version de GLPI les dossiers qui contiennent la configuration et les documents joints. Sauvegarde-les avec `tar` (note leurs chemins : ils dépendent de la version et de l'installation).
3. **Restaure dans une base de test** (jamais par-dessus la base en service) :

```bash
sudo mysql -e "CREATE DATABASE glpi_restauration CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;"
sudo mysql glpi_restauration < ~/glpi-$(date +%F).sql
sudo mysql glpi_restauration -e "SHOW TABLES;" | wc -l
sudo mysql glpi -e "SHOW TABLES;" | wc -l
```

4. Compare le **nombre de tables**, puis un **comptage** précis (par exemple le nombre d'ordinateurs dans la table correspondante : cherche son nom dans la liste des tables). Note le résultat.
5. **Supprime** la base de test.
6. Écris le **script** (S19) de sauvegarde : export daté, sortie vers le second disque, journal. Ajoute-le à `cron`. Pour la **rotation**, écris d'abord la commande qui **liste** les sauvegardes de plus de 7 jours (`find ... -mtime +7 -print`) et **vérifie sa liste** avant de passer à la suppression.

**Je comprends.**

1. Que fait `mysqldump` ? Pourquoi `--single-transaction` ? (cherche dans la documentation de MariaDB et note ce que tu trouves.) ______________________
2. Pourquoi restaurer dans une **autre base** plutôt que par-dessus ? ______________________
3. Un script de rotation avec une suppression automatique est dangereux : qu'as-tu mis en place pour le rendre sûr ? ______________________
4. Où sont les **mots de passe** nécessaires au script ? Comment éviter de les écrire dans le script ? ______________________

<details markdown="1">
<summary>Éléments de réponse</summary>

- À sauvegarder aussi : les **fichiers de configuration** de GLPI et du serveur Web, les **documents joints**, la **procédure** de restauration, et la version de GLPI utilisée (une restauration se fait vers la **même version**).
1. `mysqldump` exporte la base en instructions SQL ; l'option demande une lecture **cohérente** de la base pendant l'export (à vérifier dans la documentation).
2. Pour **tester** sans risquer de détruire la base en service ; si le test échoue, rien n'est perdu.
3. Lister avant de supprimer, tester sur un dossier de copie, journaliser ce qui est supprimé, conserver un nombre minimal de sauvegardes.
4. Dans un fichier de configuration du compte, accessible **uniquement** à ce compte (permissions restreintes), pas dans le script (voir S19).

</details>

## Partie D – Le plan de sauvegarde de JackCelair (≈ 35 min)

**Contexte.** JackCelair : 22 postes, un serveur GLPI, un partage de fichiers, un serveur de déploiement (S18), une messagerie hébergée par un prestataire. Budget limité. Un jour, un employé ouvre une pièce jointe et les fichiers du partage sont **chiffrés** par un logiciel de rançon.

**J'anticipe.** La sauvegarde est sur un NAS monté en permanence sur le serveur. Est-elle en sécurité ? ______________________

**À faire.** Rédige le plan (une page) :

1. **Inventaire** : ce qui est sauvegardé, ce qui ne l'est pas (et pourquoi).
2. **Objectifs** : RPO et RTO par élément.
3. **Règle 3-2-1** appliquée à JackCelair : quelles copies, quels supports, quelle copie hors site.
4. **Fréquence, types** (complète, incrémentale), **rotation** et durée de conservation.
5. **Sécurité** : chiffrement, accès, clés, **copie isolée** contre la rançon.
6. **Test de restauration** : qui, à quelle fréquence, avec quelle preuve.
7. **Procédure de restauration** après le scénario de rançon, en cinq étapes.
8. **Données personnelles** : ce qui est conservé, combien de temps, qui y accède.

**Je comprends.**

1. Pourquoi une copie **toujours montée** sur le serveur n'est-elle pas protégée d'un logiciel de rançon ? ______________________
2. Pourquoi un snapshot de VM ne suffit-il pas ? ______________________
3. Qui doit être **informé** lors de la restauration, et quel ticket (S15) ouvres-tu ? ______________________

<details markdown="1">
<summary>Éléments de réponse</summary>

- Plan : cohérence et justification avant tout. Éléments attendus : partage de fichiers et base GLPI avec RPO d'une journée au plus ; GLPI avec fichiers et configuration ; serveur de déploiement : l'**image maîtresse** et sa configuration ; messagerie : voir le contrat du prestataire (sauvegarde chez lui ?).
1. Le logiciel de rançon qui s'exécute avec les droits du serveur **voit** aussi le NAS monté et le chiffre ; il faut une copie **déconnectée** ou **non modifiable**.
2. Le snapshot est sur le **même stockage** que la VM ; il disparaît avec lui ou avec lui est chiffré.
3. Les utilisateurs touchés (information sur un ticket principal), la direction ; **incident majeur** possible (S17).

</details>

## Partie E – Chiffrer une sauvegarde (≈ 15 min)

**J'anticipe.** Une sauvegarde est volée avec un portable. Que risque l'entreprise si elle n'est pas chiffrée ? Et si elle l'est mais que la clé est perdue ? ______________________

> [!TIP] À toi de chercher
> Dans `man gpg`, retrouve ce que fait l'option `--symmetric` et pourquoi on précise `--cipher-algo AES256`. Résume ta trouvaille en deux phrases dans ta fiche **avant** de lancer la commande.

**À faire (dans ta VM).**

1. Prends l'archive de la partie B. Chiffre-la avec une phrase de passe : `gpg --symmetric --cipher-algo AES256 archive.tar.gz`.
2. Vérifie qu'un fichier `archive.tar.gz.gpg` a été créé et qu'il est **illisible** (`file`, `head -c 100`).
3. Déchiffre-le (`gpg --output restauration.tar.gz --decrypt archive.tar.gz.gpg`) et prouve que le contenu est identique à l'original (somme de contrôle, `sha256sum`).
4. Où ranges-tu la **phrase de passe** ? Écris la règle (qui la connaît, où elle est conservée, pourquoi pas à côté de la sauvegarde).

**Je comprends.** Quel est le coût du chiffrement pour la restauration ? Que se passe-t-il si la personne qui connaît la phrase de passe quitte l'entreprise ? ______________________

<details markdown="1">
<summary>Éléments de réponse</summary>

Sans chiffrement, un vol de support est une **fuite de données** (RGPD). Avec chiffrement, une **clé perdue** rend la sauvegarde inutilisable. Le chiffrement ajoute une étape à la restauration (à chronométrer pour le RTO) et exige une **gestion des clés** : au moins deux personnes habilitées, conservation séparée.

</details>

## Partie F – PCA et PRA : continuer, puis reprendre (≈ 40 min) <span class="technique">notion technique</span>

**Vocabulaire.** Le **plan de continuité d'activité** (PCA) vise à **maintenir** les activités essentielles pendant un sinistre ; le **plan de reprise d'activité** (PRA) vise à **reconstruire** les services après. Les objectifs RPO et RTO (cours) servent de cible.

**Contexte.** Reprends JackCelair. Le serveur du partage de fichiers est détruit par un dégât des eaux un lundi à 9 h. La facturation doit repartir le plus vite possible.

**J'anticipe.** Parmi les activités de JackCelair, lesquelles ne peuvent pas s'arrêter plus d'une journée ? ______________________

**À faire.**

1. **Hiérarchise** les services de JackCelair (partage, GLPI, déploiement, messagerie, facturation) : criticité, RPO, RTO, dépendances (utilise l'analyse de la partie A comme méthode).
2. Écris le **mode dégradé** (PCA) : comment l'entreprise continue **sans** le serveur pendant la reprise ?
3. Écris la **séquence de reprise** (PRA) : ordre de remise en service, qui fait quoi, d'où viennent les sauvegardes, comment on **vérifie** que tout fonctionne.
4. Indique **comment on teste** le plan et à quelle fréquence.

**Je comprends.**

1. Quelle différence entre PCA et PRA ? ______________________
2. Pourquoi un plan jamais testé est-il un plan non fiable ? ______________________

<details markdown="1">
<summary>Éléments de réponse</summary>

1. Le PCA permet de **continuer** (mode dégradé), le PRA de **revenir** à la normale.
2. Les sauvegardes, les accès et les documents échouent souvent au premier essai réel : seul un exercice révèle les écarts.
Évaluer la **cohérence** : dépendances respectées (on ne rétablit pas une application avant son serveur), RTO réalistes, responsabilités nommées.

</details>
