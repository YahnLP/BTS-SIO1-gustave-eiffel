### C2. La base de données (≈ 10 min)

```bash

```

Dans la console de la base :

```sql

GRANT ALL PRIVILEGES ON glpi.* TO 'glpi'@'localhost';

```

**Fuseaux horaires.** La documentation officielle demande de charger les informations de fuseaux horaires dans la base et de donner à l'utilisateur dédié le droit de lire la table des fuseaux. **Cherche** dans la page officielle la ou les commandes correspondantes et recopie-les : ______________________

**Je comprends.**

1. Pourquoi crée-t-on un **utilisateur dédié** plutôt que d'utiliser le compte `root` de la base ? ______________________
2. Que signifie `glpi.*` dans `GRANT ALL PRIVILEGES ON glpi.*` ? ______________________
3. Que fait `mysql_secure_installation` ? Cite deux réglages qu'il propose. ______________________

**Test T3 :** `mysql -u glpi -p glpi` ouvre-t-il la base ?

<details markdown="1">
<summary>Éléments de réponse</summary>

1. **Moindre privilège** : si l'application est compromise, l'attaquant n'a accès qu'à **sa** base, pas à toutes les bases ni à l'administration du serveur.
2. Toutes les **tables** (`*`) de la base `glpi`.
3. Il **sécurise** une installation de base de données : mot de passe de `root`, suppression des utilisateurs anonymes et de la base de test, interdiction de la connexion de `root` à distance.

</details>

> **Version simplifiée.** La documentation officielle recommande de **séparer** la configuration, les données variables et les journaux dans `/etc/glpi`, `/var/lib/glpi` et `/var/log/glpi`. Ce TP garde tout dans `/var/www/html/glpi` pour rester court ; en production, applique la séparation officielle.

### C4. Apache (≈ 10 min)

Crée le fichier `/etc/apache2/sites-available/glpi.conf` :

```apache
<VirtualHost *:80>
    ServerName glpi.local
    DocumentRoot /var/www/html/glpi/public

    <Directory /var/www/html/glpi/public>
        Require all granted
        RewriteEngine On
        RewriteCond %{HTTP:Authorization} ^(.+)$
        RewriteRule .* - [E=HTTP_AUTHORIZATION:%{HTTP:Authorization}]
        RewriteCond %{REQUEST_FILENAME} !-f
        RewriteRule ^(.*)$ index.php [QSA,L]
    </Directory>
</VirtualHost>
```

```bash
sudo a2dissite 000-default.conf
sudo a2enmod rewrite
sudo a2ensite glpi.conf
sudo apache2ctl configtest
sudo systemctl restart apache2
```

**Je comprends.**

1. Pourquoi la racine du site est-elle le dossier **`public`** et non `/var/www/html/glpi` ? ______________________
2. Que fait `a2enmod rewrite` ? Pourquoi `apache2ctl configtest` **avant** le redémarrage ? ______________________

**Réglages PHP.** La documentation officielle demande aussi quelques réglages de `php.ini` (temps d'exécution, taille des envois, mémoire, cookie de session, **fuseau horaire**). Trouve le fichier (`ls /etc/php`, puis `/etc/php/<version>/apache2/php.ini`), repère les paramètres dans la page officielle, applique-les et redémarre Apache. Paramètres modifiés : ______________________

**Test T2 :** depuis le client, ouvre `http://192.168.X.1/` dans un navigateur.

<details markdown="1">
<summary>Éléments de réponse</summary>

1. Seul le dossier **public** contient ce que le navigateur doit pouvoir atteindre ; le reste (code, configuration) reste **hors de portée** du Web. C'est une mesure de sécurité.
2. Il active le module de **réécriture d'URL** (utilisé par la configuration ci-dessus). `configtest` **vérifie la syntaxe** : une erreur de configuration empêcherait Apache de redémarrer et couperait le service.

</details>

<details markdown="1">
<summary>Éléments de réponse</summary>

**D1.** Le serveur **refuse** l'inventaire (ou l'ignore) : le poste n'apparaît pas. L'activation est **côté serveur**.

**D2.** 1. `RUNNOW=1` lance un inventaire **immédiatement** après l'installation. En déploiement de masse, il lancerait 200 inventaires **en même temps** (charge du serveur) ; on laisse l'agent s'exécuter à sa fréquence normale. 2. Un **service** tourne en arrière-plan, **sans session ouverte** ; il lance les inventaires à intervalles réguliers et au démarrage. 3. HTTP **sans chiffrement** : acceptable dans un laboratoire isolé ; en production, **HTTPS** avec certificat pour protéger les données de parc en transit.

**D3.** Causes fréquentes : serveur injoignable, URL avec une faute, inventaire non activé, pare-feu, agent installé sans droits. Les journaux de l'agent (dossier d'installation, sous-dossier `logs`) disent souvent la cause. La méthode pour forcer un inventaire est **à trouver dans la documentation officielle de l'agent** (option de la commande de l'agent ou interface locale) : non vérifiée ici.

</details>

<details markdown="1">
<summary>Éléments de réponse</summary>

1. L'inventaire automatique recense **tout ce qui est installé** (y compris composants système, bibliothèques, mises à jour), alors qu'une liste manuelle se limite à ce qu'on remarque.
2. InfraLab **cache** : l'installation et la sécurisation du serveur (pile Apache, PHP, base), l'activation de l'inventaire côté serveur, les paramètres réels de l'installeur (`SERVER`, `TAG`…), les vrais journaux. En revanche il **isole la notion** : découverte ≠ agent, première remontée, causes d'un agent en erreur.
3. **Un seul** serveur (GLPI) avec l'agent GLPI ; **deux serveurs** (OCS et GLPI) plus un **plugin de liaison** avec OCS. On peut rencontrer OCS dans une organisation qui l'a installé **avant** l'inventaire natif de GLPI.

Pour la maison : mise à jour automatique des versions (planifier les correctifs, repérer un logiciel obsolète), détection de changements (matériel retiré, logiciel non autorisé), préparation d'un audit de licences.

</details>
