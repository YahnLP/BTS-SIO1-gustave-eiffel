## Partie A – Première rencontre avec Docker (≈ 25 min)

**Dans DockerLab :** menu « TP d'exemple » › **Première rencontre avec Docker**. Réalise les consignes.

**J'anticipe** (avant de lancer `docker run hello-world`). Que va faire cette commande si l'image n'existe pas sur la machine ? Que va-t-il rester après la fin du programme ? ______________________

**Je comprends.**

1. Quelle est la différence entre une **image** et un **conteneur** ? ______________________
2. Après `docker run alpine echo bonjour`, le conteneur est-il en cours d'exécution ? Comment le sais-tu ? ______________________
3. **Comparaison avec une VM.** En S06, combien de temps a mis ta machine virtuelle à démarrer ? Combien de temps a mis `docker run alpine echo bonjour` ? Pourquoi un tel écart ? ______________________

**Constat du noyau.** Dans le terminal de l'hôte, tape `uname -r`. Puis tape `docker run --rm alpine uname -r`. Compare. Que constates-tu ? Qu'en déduis-tu ? ______________________

<details markdown="1">
<summary>Éléments de réponse</summary>

1. L'image est un **modèle en lecture seule** ; le conteneur en est une **instance**, avec une couche d'écriture.
2. Non : il a affiché « bonjour » puis s'est **terminé** (son processus principal s'est arrêté). `docker ps -a` le montre au statut *Exited (0)*.
3. Une VM démarre un **système complet** avec son noyau ; un conteneur démarre un **processus** sur le noyau déjà actif de l'hôte. Les durées de la VM viennent de l'élève (S06).
4. **Le même numéro de noyau** s'affiche : le conteneur n'a pas son propre noyau, il utilise celui de l'hôte. C'est la différence essentielle avec une VM.

Sortie attendue (valeur simulée de DockerLab, à titre d'exemple) : `6.8.0-45-generic` dans les deux cas.

</details>

## Partie B – Le cycle de vie d'un conteneur (≈ 30 min)

**Dans DockerLab :** TP **Le cycle de vie d'un conteneur**. Un ancien site tourne sur le port 8080 ; tu dois le remplacer.

**J'anticipe** (avant de taper `docker run -d --name web -p 8080:80 nginx`). Le port 8080 est déjà pris. Que va-t-il se passer ? Le conteneur « web » existera-t-il après cette commande ? ______________________

**Je comprends.**

1. Pourquoi le message d'erreur parle-t-il de port « already allocated » ? ______________________
2. Dans quel **état** est le conteneur « web » après l'échec ? Pourquoi ne peux-tu pas relancer la même commande sans rien faire d'autre ? ______________________
3. Que fait `docker stop` en deux temps ? Quelle est la différence avec `docker kill` ? ______________________

<details markdown="1">
<summary>Éléments de réponse</summary>

1. Un port de l'hôte ne peut être publié que par **un seul** conteneur à la fois : « test » occupe déjà le 8080.
2. **Created** : Docker a créé le conteneur avant d'échouer à le démarrer. Le **nom « web »** est donc déjà utilisé : il faut supprimer le conteneur (`docker rm web`) avant de le recréer.
3. `stop` envoie **SIGTERM** (arrêt propre), puis **SIGKILL** au bout de 10 secondes. `kill` envoie directement SIGKILL (arrêt brutal, code de sortie 137).

</details>

## Partie C – Ports et variables d'environnement (≈ 35 min)

**Dans DockerLab :** TP **Publier des ports et configurer par variables**.

**J'anticipe** (avant de lancer la base **sans** variable). L'image `postgres` démarre-t-elle sans mot de passe ? Que vas-tu voir dans `docker ps -a` ? ______________________

**Je comprends.**

1. Deux serveurs Web écoutent tous deux sur le port 80 **dans** leur conteneur. Pourquoi cela ne pose-t-il pas de problème, alors que leurs ports **publiés** doivent être différents ? ______________________
2. Pourquoi la base ne démarre-t-elle pas sans `POSTGRES_PASSWORD` ? Où as-tu lu la cause ? ______________________
3. Comment changer une variable d'environnement d'un conteneur existant ? ______________________
4. Tape `docker inspect -f "{{.Config.Env}}" db` sur la base correctement configurée. Que remarques-tu sur le mot de passe ? Quel risque cela soulève-t-il ? ______________________

<details markdown="1">
<summary>Éléments de réponse</summary>

1. Chaque conteneur a **sa propre pile réseau** : deux conteneurs peuvent utiliser le même port interne. En revanche, l'hôte n'a qu'**un seul** port 8080 : on publie vers 8080 et 8081.
2. L'image **exige** cette variable ; la cause est dans `docker logs db` (« Database is uninitialized and superuser password is not specified »), et `docker ps -a` montre *Exited (1)*.
3. On **supprime et on recrée** le conteneur avec la nouvelle variable.
4. Le mot de passe apparaît **en clair** dans la liste des variables : toute personne qui peut lancer `docker inspect` le lit. On évite d'y mettre un vrai mot de passe de production.

</details>

## Partie D – Volumes : garder ses données (≈ 35 min)

**Dans DockerLab :** TP **Volumes : garder ses données quand le conteneur disparaît**.

**J'anticipe** (avant de supprimer le conteneur `web`). La page modifiée existera-t-elle encore dans un nouveau conteneur ? Oui ou non, et pourquoi ? ______________________

**Je comprends.**

1. Où se trouvaient tes données avant d'utiliser un volume ? Pourquoi disparaissent-elles avec le conteneur ? ______________________
2. Après `docker rm -f web`, qu'est-ce qui a disparu, qu'est-ce qui est resté ? ______________________
3. Quelle est la différence entre le test avec `--rm` sans volume et le test avec un volume ? ______________________
4. Un volume te protège-t-il d'un incendie dans la salle serveur ? D'une suppression par erreur du volume ? ______________________

<details markdown="1">
<summary>Éléments de réponse</summary>

1. Dans la **couche d'écriture** du conteneur, détruite avec lui.
2. Le **conteneur** a disparu ; le **volume** `site` est resté et peut être monté dans un autre conteneur.
3. Sans volume, le conteneur neuf ne retrouve pas le fichier ; avec un volume monté au même endroit, il le retrouve.
4. **Non** dans les deux cas : un volume est sur le disque du serveur. Il faut une **sauvegarde** (S20).

</details>

## Partie E – Mission : le site et la base de JackCelair (≈ 40 min)

**Contexte.** L'entreprise JackCelair (S08) veut héberger un **petit site Web** et sa **base de données** sur un serveur de conteneurs. Contraintes de l'équipe sécurité : la **base ne doit pas être accessible de l'extérieur** ; le **site doit survivre** à une mise à jour de son conteneur.

Démarre un **nouveau laboratoire vide** dans DockerLab. Tiens le [journal de commandes](tp/journal-de-commandes.txt).

### Cahier des charges

| Élément | Exigence |
|---|---|
| Réseau | `jackcelair-net` |
| Volumes | `jc-site` (pages du site) et `jc-db` (données de la base) |
| Base | conteneur `jc-db`, image `postgres`, variables `POSTGRES_PASSWORD` (au choix, **fictif**) et `POSTGRES_DB=jackcelair`, volume `jc-db` monté sur `/var/lib/postgresql/data`, sur le réseau, **aucun port publié** |
| Site | conteneur `jc-web`, image `nginx`, port **8080** de l'hôte vers le port **80**, volume `jc-site` monté sur `/usr/share/nginx/html`, sur le réseau |
| Page d'accueil | contient « Bienvenue chez JackCelair » (écrite **dans le volume**) |

### E1. Prévoir

**J'anticipe.** Fais un **schéma** (papier ou texte) : conteneurs, réseau, volumes, port publié. Marque ce qui est visible depuis l'extérieur. ______________________

**J'anticipe.** Dans quel **ordre** vas-tu créer les éléments ? Pourquoi ? ______________________

### E2. Réaliser

Réalise le déploiement avec les commandes du cours. Les commandes que tu ne peux pas deviner sont dans l'**aide repliée** ci-dessous : cherche d'abord dans le [cours](01-cours.md) et l'[aide-mémoire](03-aide-memoire.md).

<details markdown="1">
<summary>Aide (à ouvrir après avoir cherché)</summary>

```bash
docker network create jackcelair-net
docker volume create jc-site
docker volume create jc-db
docker run -d --name jc-db --network jackcelair-net \
  -e POSTGRES_PASSWORD=exemple-fictif -e POSTGRES_DB=jackcelair \
  -v jc-db:/var/lib/postgresql/data postgres
docker run -d --name jc-web --network jackcelair-net -p 8080:80 \
  -v jc-site:/usr/share/nginx/html nginx
docker exec jc-web sh -c "echo Bienvenue chez JackCelair > /usr/share/nginx/html/index.html"
```

Dans DockerLab, si le terminal n'accepte pas une commande sur plusieurs lignes, tape-la sur **une seule ligne**, sans les `\`.

</details>

### E3. Prouver

Pour chaque preuve : **J'anticipe** le résultat, tape la commande, **capture**, explique.

| # | Preuve | Commande | J'anticipe | Je constate |
|---|---|---|---|---|
| P1 | Les deux services tournent ; seul le site publie un port | `docker ps` | | |
| P2 | La page personnalisée est servie | `curl http://localhost:8080` | | |
| P3 | Un conteneur client **sur le réseau** joint la base **par son nom** | `docker run --rm --network jackcelair-net alpine ping -c 1 jc-db` | | |
| P4 | Un conteneur client **hors du réseau** ne la joint pas | `docker run --rm alpine ping -c 1 jc-db` | | |
| P5 | Le site survit à sa suppression | `docker rm -f jc-web`, puis recréer `jc-web` (même commande qu'en E2, sans réécrire la page), puis `curl http://localhost:8080` | | |
| P6 | Volumes et réseau visibles | `docker volume ls` et `docker network inspect jackcelair-net` | | |

### E4. Comprendre

1. Pourquoi la base n'a-t-elle **aucun port publié** ? Que devrait-on changer si l'équipe sécurité l'exigeait ? ______________________
2. Pourquoi P3 réussit et P4 échoue ? Quel service de Docker résout le nom `jc-db` ? ______________________
3. Si tu avais lancé `jc-web` **sans** volume, que serait-il arrivé à ta page à l'étape P5 ? ______________________
4. Tu as fixé `POSTGRES_PASSWORD` dans la commande. Où ce mot de passe est-il lisible ? Cite **une** mesure pour limiter le risque. ______________________
5. Le serveur tombe en panne et son disque est détruit. Les volumes sont-ils sauvés ? Que faudrait-il avoir prévu ? ______________________

<details markdown="1">
<summary>Éléments de réponse</summary>

1. Pour **limiter la surface d'exposition** : seul le site a besoin d'être joint de l'extérieur ; la base est jointe par le site à travers le réseau. Si on devait l'ouvrir, on publierait `-p 5432:5432` (et on filtrerait l'accès par un pare-feu).
2. P3 : le client est sur `jackcelair-net`, réseau utilisateur avec **DNS interne** qui résout le nom du conteneur. P4 : le client est sur le réseau par défaut, où les noms ne sont **pas** résolus (et les réseaux sont isolés).
3. Elle aurait **disparu** avec le conteneur : le nouveau `jc-web` aurait affiché la page nginx par défaut.
4. Dans l'**historique** du terminal et dans `docker inspect` (variables d'environnement). Mesures : ne pas partager l'historique, utiliser un mot de passe fictif dans les TP, et, en production, un mécanisme de gestion des secrets.
5. **Non** : les volumes sont sur ce disque. Il fallait une **sauvegarde** externe (S20).

</details>

### E5. Pour les plus rapides (facultatif)

1. **Casse volontairement** la base : supprime-la (`docker rm -f jc-db`) puis recrée-la **sans** `POSTGRES_PASSWORD`. Diagnostique avec la méthode `ps -a → logs → inspect`. Corrige.
2. Dans DockerLab, enchaîne les TP **Dépannage**, **Réseaux Docker** et **Faire le ménage sur un hôte encombré**.

## Partie F – La preuve réelle : Docker dans une VM Debian (≈ 25 min)

**Pourquoi.** Le simulateur t'a fait comprendre ; ici tu fais **tourner un vrai conteneur** sur une vraie machine virtuelle (celle de S06), et tu laisses une **trace** que tu pourras verser à ton portfolio.

> [!WARNING]
> Il faut que la VM ait accès à Internet (mode NAT) et que le réseau du CFA laisse passer les dépôts Debian et le registre d'images. **Si ce n'est pas le cas**, dis-le à l'enseignant : tu feras cette partie chez toi ou en entreprise (avec accord), et tu garderas les captures.

**À faire (dans ta VM Debian, avec un compte autorisé à utiliser `sudo`).**

1. Installe Docker avec le paquet de la distribution : `sudo apt update` puis `sudo apt install docker.io`. Vérifie : `sudo docker --version`.
2. Lance `sudo docker run hello-world`, puis `sudo docker run --rm alpine uname -r` et compare avec `uname -r`.
3. Publie un vrai serveur Web : `sudo docker run -d --name web -p 8080:80 nginx`, puis `curl http://localhost:8080`.
4. Montre le conteneur (`sudo docker ps`), ses journaux (`sudo docker logs web`), puis supprime-le (`sudo docker rm -f web`).
5. **Prends une capture** de chaque étape (commande **et** résultat), avec la date visible.

**Je comprends.**

1. Qu'est-ce qui diffère entre ce que tu as vu dans DockerLab et dans la VM ? ______________________
2. Pourquoi les commandes demandent-elles `sudo` ici ? Que dit cela sur les droits nécessaires en entreprise ? ______________________

<details markdown="1">
<summary>Éléments de réponse</summary>

1. Dans la VM : téléchargements réels (durée, besoin d'Internet), messages réels. La logique (image, conteneur, port) est la même.
2. Le service Docker s'exécute avec des droits élevés ; qui peut l'utiliser est donc une question de **sécurité** (accès à Docker ≈ accès administrateur). En entreprise, ce n'est pas donné à tout le monde.

</details>
