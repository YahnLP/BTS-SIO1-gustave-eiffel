## Partie A – Un script de création de comptes (≈ 50 min)

**Contexte.** Le fichier [`utilisateurs.csv`](tp/utilisateurs.csv) liste les personnes à créer : `login;prenom;nom;service`. Copie-le sur ta VM.

**J'anticipe.** Ouvre le fichier et repère ses **défauts**. Combien en trouves-tu ? Lesquels feraient **échouer** ou **mal créer** des comptes si un script les traitait sans contrôle ? ______________________

**Cahier des charges du script `creer_comptes.sh`.**

| # | Exigence |
|---|---|
| 1 | Reçoit le **fichier** en argument ; erreur claire si l'argument manque ou si le fichier n'existe pas |
| 2 | Ignore l'**en-tête** et les **lignes vides** |
| 3 | **Refuse** (et journalise) toute ligne invalide : identifiant vide, avec espace ou majuscule, ou nombre de colonnes différent de 4 |
| 4 | Pour chaque ligne valide : crée le **groupe** du service s'il n'existe pas, puis le **compte** (dossier personnel, interpréteur Bash, nom complet en commentaire, groupe du service) **s'il n'existe pas** |
| 5 | Option `--test` : affiche ce qui **serait** fait, sans rien modifier |
| 6 | **Journal** daté (une ligne par ligne traitée : date, identifiant, résultat) |
| 7 | À la fin : un **résumé** (créés, déjà existants, refusés) et un **code de retour** non nul s'il y a eu des refus |
| 8 | **Idempotent** : une deuxième exécution ne crée rien et n'échoue pas |

**Démarche imposée.** (1) Écris d'abord les étapes en **français** ; (2) écris le script pour **un seul** utilisateur en dur ; (3) ajoute la boucle de lecture ; (4) ajoute les contrôles ; (5) ajoute `--test` ; (6) ajoute le journal et le résumé. **Teste après chaque étape.**

<details markdown="1">
<summary>Aide : commandes utiles (à ouvrir après avoir cherché)</summary>

```bash
getent passwd NOM          # le compte existe-t-il ? (code de retour 0 si oui)
getent group NOM           # le groupe existe-t-il ?
sudo groupadd NOM          # créer un groupe
sudo useradd -m -s /bin/bash -c "Prénom Nom" -g GROUPE NOM   # créer un compte
id NOM                     # vérifier
date '+%F %T'              # date et heure pour le journal
while IFS=';' read -r login prenom nom service reste; do ... done < fichier
```

Un nombre de colonnes incorrect se détecte, par exemple, en lisant aussi un champ « reste » : s'il est non vide, il y a une colonne en trop ; s'il manque un champ, `service` est vide.

Un identifiant valide peut se contrôler avec une expression régulière, par exemple dans `[[ "$login" =~ ^[a-z][a-z0-9._-]{1,31}$ ]]`.

</details>

**À faire.**

1. Écris le script, **commenté** : chaque bloc commence par une ligne qui dit **pourquoi**.
2. Lance-le d'abord avec `--test`, puis en réel, puis **une deuxième fois**. Conserve les trois sorties et le journal.
3. Vérifie avec `getent passwd`, `id` et `ls /home`.
4. **Nettoie** après le test (suppression des comptes de test).

**Je comprends.**

1. Pourquoi un mode `--test` est-il indispensable avant un traitement de masse ? ______________________
2. Quelles lignes du fichier ont été refusées et pourquoi ? Y en a-t-il que ton script a acceptées à tort ? ______________________
3. Comment sais-tu que ton script est **idempotent** ? Quelle preuve as-tu ? ______________________
4. Où mettrais-tu le **mot de passe initial** des comptes ? Pourquoi pas dans le fichier ? ______________________
5. Que se passerait-il si le script était lancé **sans** contrôle des lignes ? Donne un exemple. ______________________

<details markdown="1">
<summary>Éléments de réponse</summary>

- Défauts : **doublon** (`amartin`), **ligne vide**, **majuscules** (`FDURAND`), **espace** (`i petit`), **colonne manquante** (`hmorel`), **colonne en trop** (`jroux`). L'accent dans un prénom est **valide** (il faut juste que le script le supporte).
1. Il **montre l'effet** sans risque : en cas d'erreur de données ou de logique, on corrige avant de toucher aux comptes.
2. Les lignes de défaut ci-dessus ; le doublon est signalé comme **déjà existant**, pas refusé. Les réponses des étudiants varient : exiger la **justification**.
3. La deuxième exécution **ne crée rien**, ne produit pas d'erreur et le résumé le dit ; la preuve est la sortie et le journal.
4. Jamais dans le script ni dans le fichier (lisibles par d'autres, conservés dans les sauvegardes). On passe par un mécanisme séparé : mot de passe temporaire à changer à la première connexion, ou secret transmis par un autre canal.
5. Exemple : un identifiant avec espace crée un compte inattendu ou une erreur ; une ligne vide crée un compte sans nom ; un doublon fait échouer la création.

</details>

## Partie B – Planifier un rapport avec `cron` (≈ 30 min)

**Contexte.** JackCelair veut un **rapport quotidien** de l'espace disque, daté, dans un dossier de rapports.

**J'anticipe.**

1. Que signifie `30 7 * * 1-5` ? Et `*/5 * * * *` ? ______________________
2. Pourquoi, en TP, planifier d'abord **toutes les minutes** avant la fréquence réelle ? ______________________

**À faire.**

1. Vérifie que `cron` est actif (`systemctl status cron`) ; installe-le au besoin avec `apt`.
2. Écris un petit script `rapport_disque.sh` (**chemin absolu** partout) qui écrit dans `~/rapports/disque-AAAA-MM-JJ.txt` : la date, puis la sortie de `df -h`. Teste-le à la main.
3. Ajoute-le à ta table `cron` (`crontab -e`) **toutes les minutes**. Attends trois minutes, puis regarde le dossier. La sortie d'erreur est-elle conservée ?
4. Si tu écris la date directement dans la **ligne de crontab**, qu'observes-tu ? Pourquoi ? (Indice : cours §4.) Corrige.
5. Passe à la **fréquence réelle** (tous les jours à 7 h 30) et supprime la ligne de test.

**Je comprends.**

1. Pourquoi les **chemins absolus** ? ______________________
2. Que fait la redirection `>> fichier 2>&1` ? Pourquoi est-elle utile avec `cron` ? ______________________
3. Le rapport s'est arrêté de se produire, personne ne l'a remarqué pendant un mois. Quelle mesure de **supervision** proposes-tu ? ______________________

<details markdown="1">
<summary>Éléments de réponse</summary>

1. 7 h 30 du lundi au vendredi ; toutes les 5 minutes.
2. On **voit le résultat** tout de suite ; on évite d'attendre un jour pour découvrir une faute.
- Piège du `%` : dans une ligne de crontab, il est interprété comme une fin de ligne : il faut le **protéger** (`\%`) ou déporter la date dans le script.
1. `cron` a un **environnement minimal** (pas de dossier courant ni de variables habituelles) : un chemin relatif ne se résout pas.
2. Elle **ajoute** la sortie standard à un fichier et **envoie aussi les erreurs** au même endroit ; sans cela, les messages sont perdus.
3. Vérifier la **présence** du rapport du jour (autre tâche ou outil de supervision), alerter si absent.

</details>

## Partie D – La mission de S11 en un fichier (≈ 35 min)

> [!NOTE]
> **TP hors catalogue.** Ce TP ne fait pas partie des TP intégrés à DockerLab : les consignes sont ici, et tu les joues dans un **nouveau laboratoire vide** de DockerLab (bouton « Nouveau »).

**Contexte.** En S11, tu as monté le site et la base de JackCelair **avec une dizaine de commandes**. Tu les décris maintenant dans **un seul fichier** `compose.yaml`.

**Cahier des charges (identique à S11).**

| Élément | Exigence |
|---|---|
| Réseau | Celui du projet (créé par Compose) |
| Base | service `db`, image `postgres`, variables `POSTGRES_PASSWORD` (fictif) et `POSTGRES_DB=jackcelair`, **volume nommé** pour `/var/lib/postgresql/data`, **aucun port publié** |
| Site | service `web`, image `nginx`, port **8080** de l'hôte vers **80**, pages dans un volume ou un dossier monté sur `/usr/share/nginx/html` |
| Page d'accueil | contient « Bienvenue chez JackCelair » |

**J'anticipe.** Écris le **squelette** du fichier (clés de premier niveau) avant de le taper : ______________________

**À faire.**

1. Dans DockerLab, crée un dossier de projet, le fichier `compose.yaml` et la page d'accueil (éditeur `nano` du terminal de DockerLab).
2. Valide avec `docker compose config`, puis lance avec `docker compose up -d`.
3. **Prouve** que cela fonctionne : `docker compose ps`, `curl http://localhost:8080`, et que la **base n'est pas publiée**.
4. **Détruis puis recrée** : `docker compose down`, puis `docker compose up -d`. Les **données du volume** ont-elles survécu ? La page est-elle toujours servie ?
5. Compare avec S11 : nombre de commandes, risque d'erreur, relance.

**Je comprends.**

1. Quel est le service qui joint l'autre par son **nom** ? Quel nom utilise-t-il ? ______________________
2. Pourquoi `down` ne supprime-t-il pas les données ? Que faudrait-il ajouter pour les supprimer aussi ? ______________________
3. Si un collègue clone ton fichier, que doit-il changer avant de l'utiliser ? ______________________
4. Le mot de passe de la base est dans le fichier : quels risques ? Quelle bonne pratique proposes-tu ? ______________________

<details markdown="1">
<summary>Éléments de réponse</summary>

- Squelette : `services:` (avec `db:` et `web:`), `volumes:` en bas.
1. Le site joint la base par le nom de **service** (`db`), qui sert de nom DNS dans le réseau du projet.
2. Parce que les **volumes nommés** survivent à la suppression des conteneurs ; pour les supprimer aussi, il faut une option dédiée de `down` (cherche-la dans l'aide de la commande).
3. Le **mot de passe**, éventuellement les **ports** si déjà utilisés, et le chemin du dossier monté.
4. Lisible par quiconque lit le fichier ou son dépôt. Bonne pratique : un fichier de variables **non versionné** ou un mécanisme de gestion des secrets ; **jamais** de mot de passe réel dans un fichier partagé.
- Fichier d'exemple, à comparer sans le donner avant : une section `services` avec `db` et `web`, un volume nommé pour la base, un dossier monté pour les pages, `ports: "8080:80"` pour le site seulement.

</details>

<details markdown="1">
<summary>Éléments de réponse</summary>

Réponses discutables ; exemples : comptes à la rentrée : **à automatiser** (fréquent, compris) ; arbitrage : **ne pas automatiser** (jugement) ; rapport disque : **à automatiser** ; réinstallation annuelle : **à documenter d'abord**, voire à décrire en fichier déclaratif ; suppression de comptes : **à automatiser avec prudence** (mode d'essai, validation humaine, sauvegarde, car l'erreur est difficile à défaire).
