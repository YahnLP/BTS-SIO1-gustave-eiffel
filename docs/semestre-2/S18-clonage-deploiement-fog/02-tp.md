## Contraintes

- **Réseau isolé uniquement.** Le serveur FOG peut fournir un DHCP : **jamais** sur le réseau de l'établissement. Vérifie que ta carte réseau est bien en **réseau interne** avant de lancer l'installation.
- **La documentation officielle de FOG fait foi** : note la version et compare les questions de l'installeur avec celles de ce document.

## Partie A – Préparer le réseau et installer le serveur (≈ 55 min)

### A1. Préparer les machines (≈ 15 min)

| Machine | Rôle | Réseau |
|---|---|---|
| **Serveur** | Debian vierge, 2 cœurs, 2 Go de mémoire minimum | une carte en **réseau interne** (nom commun aux trois machines) ; une carte NAT si le serveur doit télécharger FOG |
| **Modèle** | Debian installée, **petit disque** | réseau interne |
| **Cible** | VM **vide**, disque de taille **au moins égale** à celui du modèle | réseau interne |

**J'anticipe.**

1. Pourquoi le serveur a-t-il besoin d'une **carte NAT** et d'une carte interne, alors que le modèle et la cible n'ont besoin que de l'interne ? ______________________
2. Que risques-tu en laissant la carte du serveur en **pont** pendant l'installation avec DHCP activé ? ______________________
3. Dans quel ordre le **modèle** doit-il démarrer (disque dur ou réseau) pour le TP, et quand faut-il changer ? ______________________

**À faire.** Configure les cartes réseau, donne au serveur une adresse **fixe** sur la carte interne, vérifie l'accès Internet (mise à jour des paquets) et fais un **snapshot** `avant FOG`.

<details markdown="1">
<summary>Éléments de réponse</summary>

1. Le serveur télécharge le logiciel et ses paquets (Internet par NAT) et **sert** les postes (réseau interne). Les postes n'ont besoin que du serveur.
2. Il distribuerait des adresses sur le réseau de l'établissement et **perturberait** les postes réels (second serveur DHCP).
3. Le modèle démarre d'abord sur le disque pour l'installation, puis sur le **réseau** pour l'enregistrement et la capture. La cible démarre sur le réseau.

</details>

### A2. Installer FOG (≈ 40 min)

> [!WARNING]
> **Commandes de référence.** Elles reprennent la page d'installation officielle de FOG 1.6 consultée à la rédaction. Les noms de branche et les questions **changent selon la version** : **compare avec la page de ta version** et note l'écart.

Les commandes (en `root`, via `sudo -i`) :

```bash
apt-get -y install git
cd /root
git clone https://github.com/FOGProject/fogproject.git
cd fogproject
git fetch --all
git checkout working-1.6
cd /root/fogproject/bin
./installfog.sh
```

**J'anticipe.** À ton avis, quelles décisions l'installeur va-t-il te demander ? (au moins quatre) ______________________

**À faire.** Réponds aux questions de l'installeur et **note chacune dans le journal** avec ta réponse et ta justification. Points de la documentation officielle :

- **Mode d'installation** : serveur FOG complet (et non nœud de stockage).
- **Interface réseau** : celle du **réseau interne**.
- **DHCP** : sur ce réseau isolé **sans autre DHCP**, active le DHCP de FOG ; réponds aux questions associées (routeur, DNS).
- **HTTPS** : facultatif ; en cas de doute, la documentation conseille de répondre « non ».

L'installeur te demande ensuite d'ouvrir l'**interface web** pour **créer ou mettre à jour la base de données**, et de **revenir valider** dans le terminal : ne valide qu'après cette étape.

**Je comprends.**

1. Que fait `git clone` ? Pourquoi `git checkout` d'une branche précise plutôt que celle par défaut ? ______________________
2. Où l'installeur garde-t-il tes réponses ? À quoi cela sert-il si tu relances l'installation ? ______________________
3. En cas d'échec, où cherches-tu la cause ? ______________________

**Sécurité.** Connecte-toi à l'interface web. Les identifiants d'une première installation sont donnés par la documentation (**vérifie-les**). **Change-les** et note-le dans le test T2. Pourquoi est-ce **critique** pour un serveur de déploiement ? ______________________

**Tests T1 et T2 du journal.** Fais un **snapshot** `FOG installé`.

<details markdown="1">
<summary>Éléments de réponse</summary>

- Décisions : système détecté, mode d'installation, interface réseau, DHCP et DNS, HTTPS, nom d'hôte, récapitulatif.
1. `git clone` **copie** le dépôt du projet ; la branche par défaut n'est pas forcément celle de la version voulue (ici, le schéma de base de données diffère selon la version).
2. Dans un fichier de réglages du serveur (la documentation donne son emplacement) ; au prochain lancement, l'installeur saute les questions et passe au récapitulatif.
3. Dans les journaux d'installation du dossier `bin` du dépôt (noms indiqués par la documentation).
- **Critique** : qui contrôle le serveur de déploiement contrôle **tous les futurs postes** ; des identifiants connus de tous sont une faille.

</details>

## Partie B – Enregistrer et capturer le poste modèle (≈ 40 min)

**J'anticipe.**

1. Que contient l'image d'un poste modèle ? Qu'est-ce qui ne devrait **pas** s'y trouver ? ______________________
2. À ton avis, quels éléments du modèle seront **identiques** sur la cible ? ______________________

**À faire** (étapes de la documentation officielle ; **note le nom exact** des menus que tu vois) :

1. **Enregistrer le poste** : démarre le **modèle sur le réseau** (PXE) ; dans le menu FOG, choisis l'**enregistrement rapide** avec inventaire ; éteins le poste à la fin. **Test T3 et T4.**
2. **Créer l'image** dans l'interface web (gestion des images, nouvelle image), valeurs par défaut, nom explicite (par exemple `debian-modele-v1`).
3. **Associer l'image à l'hôte** (gestion des hôtes, fiche du poste, champ image, mise à jour).
4. Dans la **fiche de l'hôte**, **tâches de base**, **capture**.
5. **Démarre le modèle sur le réseau** : la capture se lance **directement**, sans menu. Note la **durée** et la **taille** de l'image.

**Je comprends.**

1. Pourquoi crée-t-on **d'abord** la tâche, puis on démarre le poste ? ______________________
2. Qu'est-ce qui détermine la **durée** d'une capture ? ______________________
3. Ton poste modèle porte-t-il des **données personnelles** ou des **secrets** (mots de passe, clés) ? Que fais-tu ? ______________________

**Test T5.**

<details markdown="1">
<summary>Éléments de réponse</summary>

- L'image est une **copie du disque** avec ses partitions. Elle ne doit contenir ni **documents personnels**, ni **mots de passe ou clés** d'un utilisateur.
- Identiques : tout le contenu (système, logiciels, réglages), y compris des éléments censés être uniques (voir partie C).
1. Le poste, en démarrant, **cherche sa tâche** sur le serveur : sans tâche, il affiche simplement le menu.
2. La **vitesse du réseau** et des disques, la **taille** des données.
3. Réponse selon la VM : si oui, on **nettoie le modèle** et on recapture.

</details>

## Partie C – Déployer sur le poste cible et vérifier les identités (≈ 30 min)

> [!WARNING]
> **Le déploiement remplace le contenu du disque cible.** Vérifie que la VM cible est bien celle prévue (disque vide) avant de lancer.

**J'anticipe.** Quand la cible aura fini de se déployer, quels éléments seront **en double** avec le modèle ? ______________________

**À faire.**

1. Démarre la **cible** en PXE. D'après la documentation, un poste non enregistré propose l'**enregistrement complet** avec inventaire : réponds aux questions du mode texte (nom d'hôte, image, et **déploiement immédiat**) et saisis les identifiants de l'interface web.
2. La cible redémarre, copie l'image, puis démarre sur le système cloné. **Test T6.** Note la **durée**.
3. **Compare** les deux postes (nom d'hôte, adresses, identifiant de machine, clés SSH du serveur si installé). Remplis le tableau de la section 5 du journal. **Test T7.**
4. **Personnalise** la cible : un nom propre et, si besoin, la régénération de ce qui est identique. Note tes commandes.

**Je comprends.**

1. Quels éléments identiques posent un **vrai problème** sur un réseau ? Lesquels sont sans conséquence ? ______________________
2. Sur Windows, la documentation FOG indique de préparer le modèle avec **sysprep**. D'après toi, que fait cet outil et pourquoi est-il nécessaire ? (Cherche l'explication dans la documentation de l'éditeur.) ______________________
3. Quelle différence entre déployer **une** image sur un poste et la diffuser en **multidiffusion** sur vingt ? ______________________

<details markdown="1">
<summary>Éléments de réponse</summary>

- Posent problème : **nom d'hôte** (doublon), clés SSH du serveur et identifiant de machine (outils de gestion et de supervision qui confondent les machines). L'adresse IP vient du DHCP : sans conséquence si elle est attribuée automatiquement.
- Sysprep **généralise** l'installation Windows pour que chaque clone reçoive une identité propre (c'est la raison d'être de l'outil ; **vérifie** dans la documentation de l'éditeur).
- Multidiffusion : le serveur envoie **une seule fois** le flux à plusieurs postes, ce qui garde une durée comparable pour un ou vingt postes (d'après la documentation de FOG).

</details>

## Partie D – InfraLab, TP 30 « Réaffectation d'un poste » (≈ 45 min, individuel)

Un poste déployé n'est qu'un début : il doit être **suivi**. Dans **[InfraLab](https://yahnlp.github.io/InfraLab/)**, le TP 30 traite le départ d'un utilisateur : le poste PC21 est **restitué**, **préparé** puis **confié** à une nouvelle personne.

**J'anticipe.** Dans cette situation, à quel moment un **nouveau déploiement** de l'image serait-il justifié ? Que doit-on faire des **données** de l'ancien utilisateur ? ______________________

**À faire.** Réalise le TP 30, **exporte le compte rendu** et enregistre le projet en `.infralab.json`.

**Je comprends.**

1. Pourquoi **restituer** avant de réaffecter, plutôt que de changer directement l'utilisateur ? ______________________
2. L'application distingue **réalité**, **affectation** et **inventaire**. Où ton poste FOG déployé apparaîtrait-il dans **GLPI** (S13) ? Que faut-il y faire pour que l'inventaire se remplisse ? ______________________
3. Quelle étape de la procédure correspond à un **reclonage** de poste ? ______________________

<details markdown="1">
<summary>Éléments de réponse</summary>

- Un reclonage est justifié quand le poste change de mains : **retour à un état propre** (image récente), sans trace de l'ancien utilisateur. Les données doivent être **sauvegardées ou restituées** selon la procédure avant l'effacement.
1. La restitution marque la **fin de la responsabilité** de l'ancien utilisateur et conserve l'**historique** ; à chaque instant on sait qui est responsable.
2. Dans la liste des ordinateurs, une fois l'**agent** installé et l'inventaire remonté ; sans agent, le poste n'existe pas pour l'outil (S12 et S13). On peut aussi l'ajouter à la main.
3. La **préparation du poste** pour la nouvelle personne (la session de l'ancien utilisateur remplacée) : c'est la partie « réalité » du TP.

</details>
